# Development signing key

Development APKs (debug builds, application ID `io.github.saefalasalynbtel198.shcport.dev`, label "SHC Port DEV")
are signed with **one permanent development key**, so every new build installs over the previous one and keeps its
data. The key is generated and kept by the owner. CI receives it only through four GitHub Actions secrets. It is
never committed, never printed and never generated by CI.

Until 0.3.6-dev.1, CI signed with the auto-generated debug key of each build machine, a different key on every run.
Android refuses an update signed with a different key. The 0.3.5-dev.1 app (`io.github.saefalasalynbtel198.shcport`,
certificate `fcd0e71c…`) keeps that key; it stays installed unchanged as a fallback, and the development app installs
next to it.

## 1. Generate the key on your own computer (once)

You need a JDK (17 or newer) for `keytool`. Work in a folder that is not inside a Git repository or synced to the cloud.

```sh
keytool -genkeypair -v -storetype PKCS12 -keystore shc-dev.p12 -alias shcdev \
  -keyalg RSA -keysize 4096 -validity 10950 -dname "CN=SHC Port Development"
```

* `keytool` asks for the password; it is not put on the command line, so it is not saved in your shell history.
  Use a long random password.
* In a PKCS12 keystore the key password is the store password, so both secrets get the same value.
* Validity 10950 days (30 years).

**Back up `shc-dev.p12` and its password offline, in two places.** Losing either means a new key, and then one more
side-by-side change.

## 2. Certificate fingerprint (public, not a secret)

```sh
keytool -exportcert -keystore shc-dev.p12 -alias shcdev -file shc-dev-cert.der
sha256sum shc-dev-cert.der                                   # Linux
shasum -a 256 shc-dev-cert.der                               # macOS
Get-FileHash shc-dev-cert.der -Algorithm SHA256              # Windows PowerShell
```

This is the same value `apksigner verify --print-certs` reports as "certificate SHA-256 digest". `keytool -list -v`
shows it too, as uppercase with colons; both forms are accepted. Send only this fingerprint. It is pinned in
`signing/dev-certificate-sha256.txt`, and CI refuses any other key.

## 3. Base64 for the keystore secret

```sh
base64 -w0 shc-dev.p12 > shc-dev.p12.b64                     # Linux
base64 -i shc-dev.p12 -o shc-dev.p12.b64                     # macOS
[Convert]::ToBase64String([IO.File]::ReadAllBytes("$PWD\shc-dev.p12")) | Set-Content -NoNewline shc-dev.p12.b64   # Windows PowerShell
```

## 4. The four GitHub Actions secrets

GitHub → repository → **Settings → Secrets and variables → Actions → New repository secret**:

| Name | Value |
|---|---|
| `SHC_DEV_KEYSTORE_BASE64` | the single line in `shc-dev.p12.b64` |
| `SHC_DEV_KEYSTORE_PASSWORD` | the keystore password |
| `SHC_DEV_KEY_ALIAS` | `shcdev` |
| `SHC_DEV_KEY_PASSWORD` | the same password (PKCS12) |

Or with the GitHub CLI; it asks for the passwords, which keeps them out of the shell history:

```sh
gh secret set SHC_DEV_KEYSTORE_BASE64 --repo saefalasalynbtel198-a11y/stronghold-crusader-android < shc-dev.p12.b64
gh secret set SHC_DEV_KEYSTORE_PASSWORD --repo saefalasalynbtel198-a11y/stronghold-crusader-android
gh secret set SHC_DEV_KEY_ALIAS --repo saefalasalynbtel198-a11y/stronghold-crusader-android --body shcdev
gh secret set SHC_DEV_KEY_PASSWORD --repo saefalasalynbtel198-a11y/stronghold-crusader-android
```

Afterwards, delete `shc-dev.p12.b64` and `shc-dev-cert.der`, and keep only the backed-up `shc-dev.p12`.

## What CI does with it

`scripts/ci/dev-signing.sh`, used by `.github/workflows/android-build.yml` and the release workflow's development
path:

1. Unit tests and lint run first and need no key.
2. `setup` stops the build with a clear error if:
   * any of the four secrets is missing (forks never receive secrets);
   * no fingerprint is pinned;
   * the base64 or the password/alias is wrong;
   * the key's certificate differs from the pinned fingerprint.
3. The keystore is decoded only into `$RUNNER_TEMP/shc-dev-signing` (mode 0600). Passwords reach `keytool` and
   Gradle through environment variables only. GitHub masks secret values in logs, and the script prints none.
4. Gradle runs with `-PshcRequireDevKey=true` and refuses to build a debug APK without the key: there is no fallback
   to an auto-generated key.
5. The keystore is deleted after the build, also when the build fails (`cleanup`, `if: always()`).
6. `verify` checks that the APK has exactly one signer and that it is the pinned certificate. The application ID
   must be `...shcport.dev`.
7. The emulator test installs the 0.3.5-dev.1 APK first, then the new app next to it. It checks that:
   * both are installed;
   * the new app cannot read the old app's data;
   * the old app's version, certificate and files are unchanged afterwards, and it still starts.

## Checking an APK yourself

```sh
apksigner verify --print-certs app-debug.apk | grep "certificate SHA-256"
aapt2 dump badging app-debug.apk | head -1          # package: name='io.github.saefalasalynbtel198.shcport.dev' ...
```
